# hymlx

MLX implementation of **HunyuanImage-3.0-Instruct** (80B MoE, 13B active) for
Apple Silicon.

Status: **text-to-image and reference-image editing both work**, the model
writes its own prompt expansion, and every module was matched against the
official PyTorch implementation before the weights were quantised.

```
$ python3 tools/dream.py "a close-up macro photograph of a golden hamster \
      holding a sunflower seed in its paws" --steps 14
  loaded in 9s
    CoT 818 token, 78s
    sequence 6173, prefix 2073, prefill 6s
    14 steps 161s (11.5s/step) -> hamster.png
```

1024x1024 on an M5 Max / 128 GB: **about 2.5 minutes an image** at 14 steps,
or 2 minutes if you reuse the chain-of-thought. Peak memory 69.5 GiB.

---

## What is different about this model

Four things that a port of a normal diffusion transformer will get wrong:

1. **There is no separate diffusion model.** The image is generated by the same
   80B language model that writes the prompt expansion, in one autoregressive
   sequence: text, then `<boi>`, size and ratio tokens, a timestep token, then
   4096 image tokens.
2. **The image tokens use 2D RoPE on a grid centred so the image occupies the
   same average position a text span of `h*w` tokens would.** Text before and
   after the image does not need to know whether the thing in between was an
   image or a paragraph.
3. **Attention is mixed.** Text is causal; the image block attends to itself in
   full. The timestep token sits just before the image and must not see it.
4. **Editing feeds the reference image down two paths at once** — a VAE for
   pixel detail (4096 tokens) and SigLIP2 for semantics (1024 tokens) — as one
   jointly-attending block with the timestep pinned at 0.

## Install

```
pip install mlx numpy pillow safetensors transformers huggingface_hub torch
git clone https://github.com/KaedeTai/hymlx && cd hymlx
```

The official Python (tokenizer, image processor, sequence assembly) is **not
vendored here**. It is downloaded from Tencent's HuggingFace repo at run time
and imported from the cache, so you obtain it under Tencent's licence exactly
as you obtain the weights. About 2,200 lines of pure sequence logic with no
matrix multiplication in it — rewriting it would only add a second source of
bugs that drifts from upstream.

Weights: `KaedeTai/HunyuanImage-3.0-mlx-mixed4-8-hymlx` (52.5 GiB), or convert
your own from the official bf16 release with `tools/convert.py`.

## Use

```
# text to image (the model writes its own <think>/<recaption> first)
python3 tools/dream.py "a portrait photograph of an elderly fisherman" --steps 14

# reference-image editing
python3 tools/dream.py "make the hamster wear a tiny red wizard hat" \
        --image hamster.png --steps 14

# reuse a chain-of-thought, and skip CFG after step 6 (about 20% faster)
python3 tools/dream.py "..." --cot-file fox_cot.txt --cfg-steps 6
```

`tools/recaption.py` runs the text stage alone; `tools/sweep_steps.py` and
`tools/contact_sheet.py` produce step-count comparisons; `tools/requantize.py`
changes the precision of an existing checkpoint without re-downloading.

## How it was verified

Each stage was compared against the official PyTorch implementation on CPU
before the next was written. Tolerance is the reference's **own bf16 error**,
measured per module — not a guessed constant.

| stage | result |
|---|---|
| single MoE layer | 3.622e-07 (after adding `norm_topk_prob`) |
| VAE decoder | 3.692e-04 (bf16 envelope 1.167e-02) |
| VAE encoder | 7.018e-06 (bf16 envelope 8.29e-03) |
| 2D RoPE + attention mask | identical, index by index |
| decoder layer | 9.735e-07 |
| SigLIP2 + aligner | 2.357e-06 (bf16 envelope 2.567e-02) |
| patch_embed / final_layer | 4.137e-06 (bf16 envelope 4.213e-03) |
| sequence construction | mask identical to the official one |
| full 32-layer forward | **per-layer 1.035e-06** |
| flow-matching sampler | 1.667e-07 over a 50-step trajectory |

**The full-forward number is per-layer, not cumulative, and that distinction
matters.** Streaming both implementations side by side, the cumulative relative
error jumps from 4.8e-07 to 2.9e-03 at layer 12 and looks like a bug. It is
not: fed the same input, layer 12's own error is 4.1e-08 and the expert routing
is identical. What happens is that two hidden states already 4.8e-07 apart
cross a top-8 boundary — that token's experts 28 and 43 have gate weights of
**0.021299 each, equal to six decimal places**. One picks one, one picks the
other. In a MoE, cumulative error cannot tell you whether a port is correct.

The tests that need the original bf16 weights as a reference (`test_vae_*`,
`test_decoder_layer`, `test_imageio`, `test_vision`, `test_full_forward`,
`test_quant`) can no longer run here — those weights were deleted to make room.
`test_rope`, `test_sampler`, `test_conditioning` and `test_vae_roundtrip` still
run and pass. Re-downloading the official release restores the rest.

## Three bugs worth knowing about

**The tokenizer was silently broken by transformers 5.x.**
`HunyuanImage3TokenizerFast.from_pretrained()` loads the BPE model but drops
the merges and the ByteLevel pre-tokenizer, so `'a photo of a red fox...'` (43
characters) encodes to **34 single-character tokens** instead of 11, and
Chinese encodes to nothing at all. No error, no warning — just a model reading
character soup. This produced photographic-looking images with no relation to
the prompt, and cost several rounds of investigation aimed at the quantiser.
`hymlx/conditioning.py` now loads `tokenizer.json` with `tokenizers` directly
and asserts the encoding at construction.

**The VAE decodes a still image to four frames and the official wrapper keeps
the last one** (`decoded[:, :, -1:]`). Taking the first gives a razor-sharp
16-pixel lattice that reads as a broken model. That line lives in the wrapper,
not in the `Decoder` module, so tensor-by-tensor module tests cannot catch it.
`test_vae_roundtrip.py` pins it: 20.1 dB the right way, 13.9 dB the wrong way.

**4-bit was blamed for something the tokenizer did.** An early measurement
showed 4-bit's estimate of the clean latent at sigma=1.0 correlating +0.0259
with bf16 — apparently catastrophic, and the reason this port moved to 8-bit.
That measurement was taken while the tokenizer was broken. With nothing
meaningful to condition on, the model's output at maximum noise is chaotic, and
two quantisations of it disagree for reasons that have nothing to do with
quantisation. Re-measured after the fix, plain 4-bit correlates **+0.9650** and
produces perfectly good images.

## Precision

Measured after the tokenizer fix, all against the same 8-bit reference:

| configuration | weights | s/step | sigma=1.0 correlation |
|---|---|---|---|
| 8-bit g64 | 81.3 GiB | 11.0 | baseline |
| 6-bit g64 | 70.8 GiB | 10.4 | +0.9980 |
| **experts 4-bit, rest 8-bit** | **49.7 GiB** | 11.0 | **+0.9907** |
| 4-bit g64 | 48.8 GiB | 10.7 | +0.9650 |
| 4-bit g32 | 58.0 GiB | 9.7 | +0.9622 |

Three things fall out of this:

- **Group size is not the lever; bit depth is.** g32 costs 9 GiB more than g64
  and is not better (0.9622 against 0.9650).
- **Attention is the sensitive part, not the experts.** The 64 experts are
  91.7% of the parameters; dropping only them to 4-bit costs 1 GiB over full
  4-bit and lifts the correlation from 0.965 to 0.991. That is the released
  configuration.
- **Precision buys memory, not speed** (9.7-11.0 s/step across a 2x range in
  bit depth). This path is compute-bound, not bandwidth-bound.

`tools/requantize.py` converts between precisions in place. Going 8-bit ->
6-bit costs 3.2% more error than quantising from bf16 directly (theory says
sqrt(17/16) = 3.1%; eight real tensors all measured 3.2%), so there is no need
to re-download 157 GiB to change precision.

## Speed

1024x1024, CFG on, M5 Max 128 GB:

| | steps | sampling | total |
|---|---|---|---|
| text to image | 14 | 161 s | 2.7 min |
| text to image, reusing a CoT | 14 | 161 s | 2.0 min |
| reference-image editing | 14 | 182 s | 3.5 min |
| chain-of-thought alone | 1100 tok | | 100 s |

Step count: composition settles around 18 steps and texture around 22; 14 is
usable and 28 is the point of diminishing returns. Because the step count
changes the ODE trajectory, different counts give *different* images rather
than better or worse versions of one image — no scalar metric separates the two,
so `tools/sweep_steps.py` exists to let you look.

**Resolution is not adjustable.** The `ResolutionGroup` has 37 entries, all
between 0.85 and 1.05 MP; asking for 512x512 or 2048x2048 both give 1024x1024.
Only the aspect ratio moves.

What made it fast: the text prefix (system prompt, prompt, CoT — 2,000+ tokens)
is identical at every sampling step, so it is prefilled once and cached. That
also removes the attention mask entirely for the image block: image tokens
already attend to all text and to each other, and running the timestep token
through the stack first satisfies the one exception. No 6278x6278 mask to
materialise (315 MB of fp32, re-read at every layer). 20.1 s/step -> 11.9.

## Against HiDream-O1 on the same machine

Both measured the same day, 1024x1024, warmed up:

| | HiDream-O1 (mdream) | HunyuanImage-3.0 (hymlx) |
|---|---|---|
| parameters | 8.18B dense | 84.9B MoE, 13B active |
| image tokens at 1024x1024 | **1,024** | **4,096** |
| forwards per step | 1 (cfg 1.0) | 2 (cfg 2.5) |
| one image | **9.9 s** | 173 s |

17.5x slower, and the largest single factor is not model size: HiDream feeds
32x32 pixel patches straight into the transformer with no VAE, so 1024x1024 is
1,024 tokens against Hunyuan's 4,096. Roughly 6.4x of the gap is tokens,
active parameters, CFG and step count; the remaining 2-3x is that a MoE's
gather-matmul cannot saturate the hardware the way a dense GEMM does (measured
14 TFLOPS against a ~19-20 TFLOPS 8-bit ceiling).

For editing the gap narrows to 1.8x — and Hunyuan can edit at 1 MP, which
HiDream cannot (it collapses into noise below about 1.7 MP).
